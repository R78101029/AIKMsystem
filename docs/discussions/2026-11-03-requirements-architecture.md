## 起點

依據[交接摘要](../00-project/handoff.md)開啟專案。AI 助手先產出初版草稿（commit `3fcdb2f`），內容包括資料模型 v0.1、架構與範圍文件。專案負責人隨即要求**暫停實作，先討論架構與需求**。

## 第 1 輪：架構的關鍵問題

AI 助手提出 6 個待定事項：錨點、證據規格的層級、覆蓋層與檔案的關係、AI 服務層的邊界、燈號期間、多租戶。

負責人的提問與結論：

| 主題 | 討論 | 結論 |
|---|---|---|
| 錨點 | 以文件為中心時看不見「缺了什麼」；以條款為中心時，缺口才看得見 | 以條款為錨點（ADR-0001） |
| 證據規格對應多個評鑑 | MVP 需要嗎？結構用方案 B 幾乎不增加成本，之後再改則成本很高 | 結構採方案 B，功能只做單一框架（ADR-0002） |
| D/C 文件被搬走、改名、刪除 | 負責人指出：辦法類可以交給文管中心；真正的難點是 D/C；只有快照不能當佐證 | 改成在紀錄產生當下收件；原檔才是佐證（後續發展為 ADR-0004） |
| 只呼叫任務、不呼叫模型 | 以檢驗科為比喻：開單只開 CBC，不指定哪台儀器 | 同意解耦（ADR-0005） |
| 模型連線 | 負責人要求保持彈性：地端自建、客戶自己的雲端，或醫點月費代管 | 模型轉接器＋路由（ADR-0005） |
| 燈號期間 | — | 細節待定（DASH-04） |

## 第 2 輪：彈性架構

負責人：「會有多評鑑、多院區、多 API、多雲端硬碟介接的問題，因此需要彈性的架構。」

結論：
- 四個會變動的方向各自用一種機制處理：
  - 多評鑑 → 資料驅動；
  - 多院區 → 組織樹加上設定繼承；
  - 多 API → 模型轉接器；
  - 多雲端硬碟 → 儲存轉接器。
- 共通機制：核心只認介面，不認廠商；設定分層繼承；轉接器宣告自己的能力。
- 原則：**介面一次定好，MVP 每個介面只做一個實作**。

## 第 3 輪：並存視角、Agent、版本紀錄、ISO

| 主題 | 負責人意見 | 結論 |
|---|---|---|
| 上傳者無法以條款為錨點 | 希望有並存的方式 | 任務、單位、條款三種視角；證據規格做為翻譯層（ADR-0001） |
| 導入前的文件架構分析 | 可以做成另外收費的服務，用 Agent 處理，再以比較嚴格的架構強制關聯 | 採納，並納入產品（ADR-0008、0014） |
| 單位會更新或修改檔案 | 需要留下紀錄 | 只新增不覆寫；證據綁定版本；確認後若被修改，燈號轉為需重審 |
| 模組化 | 功能要能切成獨立模組，自己也比較看得懂 | 反映在資料夾結構 |
| 開發要符合 ISO | 討論紀錄、程式版本都要完整保留；要考慮部署、交付、導入 | 提出資料夾結構草案 |

## 第 4 輪：決定

負責人決定：
1. 開發流程採用 ISO/IEC 29110（ADR-0007）；
2. Agent 另開程式庫（後於第 6 輪推翻）；
3. 已確認版本另存副本，採方案 B（ADR-0004）；
4. 文件用繁中、程式用英文（ADR-0009）；
5. 現有草稿依新結構重整。

## 第 5 輪：需求分析（第一輪）回饋

- 角色清單維持開放；新增角色時加註備註。
- CON-01（一致性稽核）要留在 MVP-0。
- 權限：只有品管人員可以看全部。
- 副本存在地端儲存區。負責人擔心硬碟爆掉，並問能否放在客戶端的硬碟。結論：可以，並把副本存放位置做成轉接器；需要容量監控、去重、保存期限（ADR-0004）。
- 登入：安南用 O365，其他機構不一定，開發時要兼顧（ADR-0011）。

## 第 6 輪：權限細節、ISO 版本控制、Agent 定位

- 委員會算一個單位；主管可以看所屬單位與下層單位；**一個人可能隸屬多個單位，所以要用標籤式的成員關係**；評鑑小組與高層可以看全部內容（ADR-0010）。
- 同一份紀錄對應多個條款時只存一份，但版本控制要符合 ISO，讓需要做 ISO 的機構也能用 → 區分「文件」與「紀錄」，依 ISO 9001 7.5 設計文件管制（ADR-0012）。
- Agent 掃描要做進產品，因為文件架構和機構的產業、所參加的評鑑有關 → Agent 併回主程式庫，推翻第 4 輪的第 2 項決定（ADR-0008）；導入領域套件（ADR-0013）。
- 使用者、單位、角色需要前置對接與清單匯入（ORG-07～11）。

## 第 7 輪：文管、前置步驟、MVP-0 時程

- 文管：兩種模式都要支援（ADR-0012）。
- **負責人澄清**：重點不在擴展到其他產業。重點是很多機構沒有導入 ISO、文件很亂，**直接用評鑑需求為導向根本建不起來**，所以需要一個前置步驟。過去要由專家逐單位訪談盤點，現在可以匯入辦法、交給 Agent 處理；Agent 也可以負責稽核監控。→ 辦法驅動的導入流程（BOOT），加上稽核監控（MON）（ADR-0014）。
- MVP-0 延長到約 2 人月（ADR-0019）。

## 第 8 輪：舊 KM 的問題、辦法現況、測試資料

- **舊 KM 文管的弱點**：像比較強的雲端硬碟，可以加標籤、標注連結，但缺乏強制，最後變成網路硬碟；評鑑系統只是讓人連結資料，沒有導入 AI；評鑑進度過於空泛，而且缺乏簽署過程。→ ADR-0015（以流程強制關聯）、ADR-0016（準備度客觀計算＋簽核）。
- 安南的辦法和 SOP 都有 PDF 或 Word 檔；會議紀錄等 D/C 類很亂，散在各單位。
- MVP-0 直接用醫院通用的模擬資料，並埋入已知缺陷，兼做黃金測試集。
- BOOT-01～04 放進 MVP-0（ADR-0019）。

## 第 9 輪：簽核、D/C 位置、下一步

- **特殊流程**：例如安南的辦法在委員會通過後，還要上公文，公文通過才算生效；公文的簽核過程也要列為該文件的關聯文件。這類需求需要靠人工討論分析 → DCT-13、DCT-14、BOOT-12。
- **簽核**：指主管認可，屬於系統層級，不需要憑證簽章（ADR-0016）。
- **D/C 目前的位置**：在舊 KM 中，之後應該會回到 O365 → ADR-0017、TASK-12。
- **下一步**：選擇方案 (a)，先把需求、決策、討論寫進程式庫並重整結構，之後再討論使用情境流程。
