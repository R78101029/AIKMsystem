## 討論內容

1. **負責人決定：先做情境 1，同時進行技術驗證。**

2. **技術驗證**（詳見報告）
   - 開發環境沒有可以直接呼叫的模型 API 金鑰，改為由兩個獨立程序做盲測：一個用大型模型，一個用小型模型（粗略代表地端模型）。
   - 結果：兩者都找到 12/12 種應產生的紀錄，埋入的 4 個問題全部抓到，沒有誤抽非紀錄條文。
   - 缺口：頻率與完成時限混淆；分散在其他條文的要求沒有列成要素。
   - 意外收穫：兩個模型都自己找出了標準答案沒列、但真實存在的辦法問題。

3. **情境 1 走過一遍後，發現 6 個缺口**：
   - 同一種紀錄由多個單位各自產生（需要適用單位）；
   - 同一種紀錄被多份辦法要求（需要合併）；
   - 抽取時發現辦法本身的問題（需要轉為修訂建議）；
   - 有實際在做、但辦法沒寫的紀錄（需要補充）；
   - 匯入時要辨識辦法的編號、版次等描述資料；
   - 頻率缺少「每班」。

4. **負責人的決定**
   - 導入由**品管主導**。
   - 單位確認清單由**單位主管確認**。
   - **適用單位由單位自行勾選**。

5. **尚未回覆的兩題**：辦法問題清單的流向（暫定由品管篩選後轉給文管）、導入時程的期待（待定）。
