## 目的

把一家文件尚未整理的機構，從「一堆辦法」帶到「系統依證據規格自動產生各期任務」，取代過去由專家逐單位訪談盤點的做法。

## 參與者

| 角色 | 在本情境的職責 |
|---|---|
| R3 品管人員 | **主導導入**：審核 AI 草稿、處理例外、決定起始日 |
| R2 單位主管 | **確認本單位的確認清單**，包括勾選本單位適用的規格 |
| R5 文管中心 | 提供辦法全集；接收經品管篩選的辦法修訂建議 |
| R6 院內 IT | 前置對接：組織與人員資料、登入、儲存 |
| R7 醫點顧問 | 導入分析服務；協助訪談機構的特殊流程 |
| S1 導入分析 Agent | 抽取、合併、對應、找缺口、產出報告（只產生建議） |

## 前置條件

- 合約與授權完成，包括掃描授權與資料處理範圍（[導入檢核表](../../06-deployment/onboarding-checklist.md) A）
- 組織、人員、成員關係已匯入（ORG-07～09）
- 機構特殊流程已訪談確認（BOOT-12）
- 已選定要對應的評鑑框架，並載入醫療領域套件（FW-01、ADR-0013）

## 主要流程

| 步驟 | 執行者 | 動作與系統行為 | 需求 |
|---|---|---|---|
| 1 | 文管 → 系統 | 匯入辦法全集（Word／PDF）。系統辨識文件編號、版次、生效日、制定單位，並標出重複檔與舊版 | BOOT-01、BOOT-15 |
| 2 | Agent | 逐份抽取「應產生的紀錄」，產生證據規格草稿：紀錄名稱、頻率、**完成時限**、產生者、必備要素、出處。同時產生辦法問題清單：矛盾、不明確、引用外部規定、缺少負責人 | BOOT-02、BOOT-03、SPEC-08 |
| 3 | Agent | 跨辦法合併重複的規格，保留全部來源（例：異常事件通報同時出現在急救車辦法與異常事件辦法） | BOOT-13 |
| 4 | 品管 | 審核草稿：接受、修改、合併、退回。審核結果可以標記為黃金測試集 | BOOT-04、REV-03 |
| 5 | 品管 | 篩選辦法問題清單，轉給文管當修訂建議（*暫定*） | BOOT-14 |
| 6 | 系統 | 依辦法的適用範圍，產生各單位的確認清單：「依據這幾份辦法，貴單位可能需要產生以下紀錄」 | BOOT-05 |
| 7 | 單位主管 | 逐項確認：**本單位適用／不適用**、修正內容；補充「實際有做、但辦法沒有依據」的紀錄 | BOOT-05、SPEC-07、BOOT-16 |
| 8 | Agent → 品管 | 對應評鑑條款，並找出兩個方向的缺口：條款沒有辦法涵蓋；辦法有要求但沒有單位產生 | BOOT-06、BOOT-07 |
| 9 | （選配）Agent | 比對既有檔案（舊 KM 匯出、O365），算出每種紀錄目前已有幾期 | BOOT-09、TASK-12 |
| 10 | Agent → 品管 | 產出文件架構分析報告與可以直接匯入的設定 | BOOT-11 |
| 11 | 品管 | 設定起始日；系統從起始日開始，依「規格 × 適用單位 × 期間」產生任務 | TASK-01、ADR-0017 |

## 例外流程

| 代號 | 情況 | 處理 |
|---|---|---|
| E1 | 辦法是掃描檔 | 先做文字辨識（DOC-08）；辨識信心低的抽取結果，特別標示給品管 |
| E2 | 一份辦法抽不出任何紀錄 | 列為「無紀錄要求」，由品管確認（例如純宣示性的辦法） |
| E3 | 單位逾期沒有回覆確認清單 | 自動提醒；再逾期則通知品管，由品管追蹤或代為處理 |
| E4 | 單位勾選「不適用」，但品管認為應該適用 | 由品管裁決，並留下理由與紀錄 |
| E5 | 規格有未解決的辦法問題（例：每日與每班矛盾） | 先依條文產生任務，並標示「待釐清」；文管修訂辦法後，透過變更影響更新規格（CHG-01、DCT-10） |
| E6 | 單位補充的紀錄沒有辦法依據 | 先建立為「無辦法依據」的規格，並提醒文管評估是否補訂辦法 |

## 後置條件

- 正式的證據規格目錄，每份規格都有適用單位、頻率、完成時限、必備要素和出處
- 條款對應、雙向缺口報告
- 經品管篩選的辦法修訂建議
- 起始日之後，系統自動產生各單位的各期任務
