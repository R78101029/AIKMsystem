## 1. 適用標準

採用 ISO/IEC 29110 Basic Profile 的兩個流程：
- **PM** 專案管理
- **SI** 軟體實作

資訊安全參考 ISO/IEC 27001（[ADR-0007](../adr/0007-iso29110-process.md)）。

## 3. 文件管制（本專案自己的文件）

- 每份正式文件的開頭都要有表格，標明：文件編號、版次、狀態（草稿／審查中／核准）、日期。
- 文件的修改一律透過 PR，修改歷程以 git 為準。
- 文件**核准**的方式：專案負責人在 PR 上核准，並把文件狀態改為「核准」。
- 已核准的需求規格書即為**需求基準**。之後的變更依第 5 節處理。

## 4. 組態管理

- **分支**：`main` 是受保護的主線；開發一律在功能分支上進行，經 PR 合併。
- **版本號**：語意化版本 `vMAJOR.MINOR.PATCH`。每次發行都打標籤，並更新 `CHANGELOG.md` 與 `docs/05-release/`。
- **資料庫遷移**：檔案只新增、不修改（見[部署文件](../06-deployment/deployment.md)）。
- **提示詞與黃金測試集**也納入版本控制；修改後必須重跑評測，並把結果附在 PR 上。

## 5. 變更管理

```
Issue（需求變更或缺陷）─► 分支 ─► PR（引用需求編號／ADR）─► 審查 ─► CI 通過 ─► 合併 ─► 更新追溯矩陣
```

- 需求變更：修改需求規格書，並在 PR 說明影響範圍（設計、程式、測試、時程）。
- 架構決策的變更：新增一份 ADR 並註明取代關係，不可以刪除或改寫舊的 ADR。

## 6. 討論紀錄

- 重要的討論（包含與 AI 助手的對話）結束後，**必須**把摘要寫入 `docs/discussions/YYYY-MM-DD-主題.md`。
- 摘要內容：討論了哪些問題、負責人的意見、結論、對應的 ADR 與需求編號、未結事項。
- 原始對話不一定會被保存，所以摘要是唯一的正式紀錄。

## 7. 審查

| 審查項目 | 時機 | 審查者 |
|---|---|---|
| 需求規格書 | 基準化之前 | 專案負責人（必要時邀請試點院方） |
| 架構與 ADR | 每次新增或變更 | 專案負責人 |
| 程式碼 PR | 每次合併前 | 專案負責人；有工程師之後改為互相審查 |
| 資安 | MVP-1 上線前 | 獨立廠商 |
