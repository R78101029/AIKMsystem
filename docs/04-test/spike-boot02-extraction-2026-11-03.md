# 技術驗證報告：從辦法抽取證據規格（BOOT-02）

| 項目 | 內容 |
|---|---|
| 文件編號 | AIKM-TST-001 |
| 版次 | 1.0 |
| 狀態 | 完成（技術驗證等級，不是正式驗收） |
| 日期 | 2026-11-03 |
| 對應需求 | BOOT-02、BOOT-03、AIS-07；專案風險 #3 |
| 資料與腳本 | [`eval/boot02-extraction/`](../../eval/boot02-extraction/) |

## 1. 目的

驗證專案最核心的技術假設：**AI 能不能從醫院辦法中，抽出「應該產生哪些紀錄」，並寫成證據規格**（什麼紀錄、多久一次、誰產生、需含哪些要素、出處）。

## 2. 方法

| 項目 | 做法 |
|---|---|
| 測試資料 | 3 份模擬辦法：感染管制委員會設置辦法、急救車管理辦法、異常事件通報及處理辦法。內含 12 種應產生的紀錄 |
| 埋入的陷阱 | 條文與附表矛盾（每日／每班）、頻率不明確（「定期」）、引用其他辦法與外部規定、不會產生紀錄的條文（保密、不究責）、事件觸發加完成時限、要素分散在多個條文 |
| 標準答案 | 人工撰寫（`expected/`），在抽取完成後才放進程式庫 |
| 提示詞 | v1（[`prompt.md`](../../eval/boot02-extraction/prompt.md)） |
| 受測模型 | 雲端大型模型；雲端小型模型（粗略代表日後的地端模型） |
| 執行方式 | 盲測：由兩個獨立執行的程序分別抽取，只能讀提示詞與辦法 |
| 評分 | [`score.py`](../../eval/boot02-extraction/score.py)，以關鍵字比對，評分標準刻意寬鬆 |

## 3. 結果

| 指標 | 大型模型 | 小型模型 |
|---|---|---|
| 應產生紀錄的召回率 | 12/12（100%） | 12/12（100%） |
| 抽取結果中正確的比例 | 14/14（100%）＊ | 12/12（100%） |
| 頻率正確 | 12/12 | **11/12** |
| 事件觸發的完成時限正確 | 4/4 | 4/4 |
| 產生單位或角色正確 | 11/11 | 11/11 |
| 出處條次正確 | 12/12 | 12/12 |
| 必備要素召回率（平均） | 0.85 | 0.89 |
| 埋入問題的偵測 | 4/4 | 4/4 |
| 誤抽非紀錄條文（保密、不究責） | 0 | 0 |

＊大型模型多抽出「委員聘任紀錄」與「封條異常通報」兩項，屬於標準答案中可接受的選擇性項目。

### 錯誤與缺漏

1. **頻率與完成時限混淆**（小型模型，感管會議紀錄）
   - 它把第 6 條「會後十四日內陳核」的完成時限當成頻率，判為「事件觸發」，漏掉了第 3 條「每三個月召開一次」。
   - 根本原因：提示詞和資料模型只在事件觸發時才有「時限」欄位。但一種紀錄常常**同時**有頻率和完成時限。
2. **分散在其他條文的要求沒有列為要素**（兩個模型都有）
   - 例如主席資格（第 3 條）、出席過半（第 4 條）、會後陳核（第 6 條）、「提報委員會」這類後續步驟。
   - 模型傾向只列出「應載明」條文中明寫的內容。

### 超出預期的表現

兩個模型都找出了標準答案沒有列出、但確實存在的辦法問題，例如：
- 第 4 條寫「列印測試紙條」，附表欄位卻是「黏貼」；
- 附表有「護理長覆核」欄位，條文卻沒有規定覆核；
- 整份辦法都沒有規定紀錄的保存期限；
- 沒有指明誰負責提出監測報告。

這證明「把抽取發現的辦法問題轉為文管的修訂建議」（情境 1 的缺口 #3）是可行的，而且很有價值。

## 4. 結論

**在格式良好的辦法上，核心假設成立**：兩個模型都能找到全部應產生的紀錄，並正確判斷頻率、負責人與出處，也能指出辦法本身的問題。小型模型的表現接近大型模型，地端部署有希望。

**但還不足以宣稱已經驗證完成**，限制如下：

| 限制 | 說明 |
|---|---|
| 樣本極小 | 只有 3 份辦法、12 種紀錄 |
| 模擬辦法過於整齊 | 真實辦法可能是掃描檔、表格、舊式編號、條文很長或跨多個單位 |
| 標準答案與評分偏寬鬆 | 關鍵字比對可能高估表現；標準答案由同一個開發團隊撰寫 |
| 沒有測到地端模型 | 小型雲端模型只是粗略的代表 |
